2. Prepare Supabase

1. Open your Supabase project dashboard.

2. Choose SQL Editor → New query.

3. Open the local file deploy/supabase/001_runtime.sql, copy the complete contents into the editor, then click Run. It creates ZAR's private tables and restricted backend functions. It does not delete existing tables or add sample orders.

Then open a new SQL query, paste deploy/supabase/002_overview_v6.sql, and run it. The final result should be 33 jobs. If you already ran 001 successfully, run only 002 for this upgrade. Use this adapted file, not the original Version 6 attachment: that attachment requires a different earlier relational schema. Neither migration adds sample orders.

4. Run this separate check. Expected results: false, false, true.

select
  has_function_privilege('anon','public.zar_doc_get(text,text)','EXECUTE') as anon_allowed,
  has_function_privilege('authenticated','public.zar_doc_get(text,text)','EXECUTE') as staff_direct_access,
  has_function_privilege('service_role','public.zar_doc_get(text,text)','EXECUTE') as backend_allowed;

5. Keep the zar_private schema out of Data API exposed schemas. The default public schema must remain exposed for the restricted RPC functions. The browser does not access the tables directly.

6. Open Project Settings → API Keys. Keep your publishable key. Also create/copy a server secret key, beginning sb_secret_. Legacy service_role keys also work. Store this privately; the publishable key alone cannot save backend data. Supabase key types.

7. Open Authentication → Users → Add user → Create new user. Create zarintelligence@gmail.com with a strong password. Keep the password private. Confirm/verify this owner account using the dashboard's confirmation option or verification flow.

8. Enable the Email/password provider. Disable public sign-ups for this staff console. There is no open signup page in ZAR.

9. In Authentication → URL Configuration, set Site URL to https://app.zarintelligence.com. Invitations/recovery require approved redirect URLs and an SMTP configuration if you enable those later. This release supports password sign-in; manage password recovery through Supabase until a customer-facing recovery flow is added. Supabase Auth.

The exact verified owner email becomes the first Store6 administrator. Other users have no access until assigned a role. The attached SQLite database kit is a synthetic archive: do not paste its SQLite SQL into Supabase. Use this release's migration.

2. Install Google Cloud CLI, following Google's Windows instructions.

4. Commit and push to your private GitHub repository

If the repository already contains files: clone it into a separate folder first, then copy this release's source into that checkout, excluding .env* except examples, data, .venv, node_modules, and work. Preserve its .git folder and reconcile existing files. Do not overwrite existing history or force-push.

For an empty repository, run from the ZAR project folder:

git init -b main
git config user.name "ZAR Intelligence"
git config user.email "zarintelligence@gmail.com"
git add .
git status --short
git diff --cached --stat

Check that .env, .env.backup.*, data, passwords, keys, and service-account credentials are absent from the staged list. .env.example and .env.supabase.example contain placeholders and are safe. Ignore rules also exclude secrets from Docker, Cloud Build and the release ZIP.

git commit -m "Add ZAR V5 website and Supabase merchant console"
git remote add origin https://github.com/zarintelligence-cloud/ZAR-Intelligence.git
git push -u origin main

Use Git Credential Manager's browser sign-in with the account that can access this private repository. GitHub account passwords are not Git HTTPS passwords; if you need a personal access token, enter it only into the credential prompt, never into a repository URL.

If origin exists, inspect git remote -v. If push is rejected because the repository contains a README or other commits, use the clone-and-copy approach above; do not use --force. Open GitHub and confirm the commit appears. This stores the source; it does not deploy the app. An automated test workflow is included under .github/workflows/tests.yml.

6. Save secrets and deploy the application

The following helper asks for your Supabase server secret using hidden input. It creates zar-supabase-server-key in Google Secret Manager and generates a separate zar-admin-token for legacy operations endpoints:

.\deploy\create-secrets.ps1 -Project $ZarProject
.\deploy\preflight.ps1 -Project $ZarProject -AdminSecret zar-admin-token

No key is printed or committed. Running the helper again adds a new Supabase secret version and preserves an existing operations token.

Preview, then deploy:

.\deploy\launch-zar.ps1 -Project $ZarProject -DryRun
.\deploy\launch-zar.ps1 -Project $ZarProject

When asked, paste the publishable key. This wrapper already contains your Supabase URL and administrator email. It builds local source with Cloud Build, then deploys:

- zar-polaris: public website/API with protected staff console.

- zar-workshop: private retail specialists, invoked by Polaris using Google identity.

It configures shared Supabase records and GCS artwork storage. No separate Gemini API key is needed on this Vertex AI path; service-account permissions authorize model calls. No GitHub-to-Cloud-Build connection is needed for the first deployment.

The script creates billable resources and keeps one Polaris instance warm with CPU allocated for durable retries. Workshop can scale down. Review Cloud Run, load balancer, storage, build, Gemini and Supabase costs before running the real deployment.

Configured models: gemini-3.5-flash and gemini-3.5-flash-lite. Availability and quota must be checked by real requests in your project. If unavailable, consult Google's model lifecycle table and use the underlying deployment script's -ReasoningModel / -FastModel overrides. Do not silently fall back to demo reasoning in production.

The script prints a Polaris HTTPS URL and saves non-secret deployment URLs in data/deploy/deployment.json. Open that URL. The workshop should reject anonymous requests.

7. Verify a complete live order

1. At the Polaris URL, choose Sign in and use the Supabase owner email/password.

2. The banner should say Gemini enabled · supabase.

3. Open <POLARIS_URL>/healthz: store must be supabase, assets must be gcs, mode must be gemini. These show configuration; the workflow below proves behavior.

4. Choose Start order, upload a test PNG/JPEG/WebP logo and enter:

2 cricket jerseys, half sleeves, navy and gold, names and numbers,
budget 25000 INR, required by 30 November 2026.

Use a future date if testing later. Answer any missing-detail questions.

5. Tick This is a synthetic test order before creating this acceptance order. Check that three proof images show your actual uploaded logo. Choose a proof.

6. Open the roster form. Add two distinct names, valid sizes and different jersey numbers. Return to the console; it refreshes every ten seconds.

7. Review the INR quote and delivery estimate. Check the customer-approval box and confirm. Supplier handoff remains sandbox unless explicitly connected.

8. Download the production specification. Reload and sign out/in: the order and proofs must remain.

9. Check actual model names and successful runs under Agent traces. Under Decision audit, mark a decision reviewed and reload to check persistence.

10. Check the saved order in Supabase SQL Editor:

select key as order_id, body->>'state' as state,
       body #>> '{quote,quote,total}' as quote_total
from zar_private.documents
where collection='sessions'
order by updated_at desc;

If it fails, inspect Cloud Run → service → Logs. Common causes: SQL migration missing, wrong secret, paused Supabase project, Gemini quota/access, or missing workshop invocation permission. Do not share logs containing secrets or customer data. A successful container deployment alone is not a successful end-to-end test.

8. Connect GoDaddy and HTTPS

Use Google's external Application Load Balancer for this production domain. See Cloud Run domain options.

Run this once, after the application works at its run.app URL:

.\deploy\connect-domain.ps1 -Project $ZarProject -DryRun
.\deploy\connect-domain.ps1 -Project $ZarProject

It reserves a static IP, creates an HTTPS load balancer, and requests a certificate for app.zarintelligence.com. Write down the printed IP. If it stops on an existing resource, inspect that resource in Google Cloud before continuing; do not delete it to rerun blindly. Later releases use launch-zar.ps1 only.

In GoDaddy:

1. Sign in → Domain Portfolio / My Products → zarintelligence.com → DNS.

2. If its nameservers point to another DNS provider, edit there instead.

3. Add this record using the actual IP from Google:

TypeNameValueTTL
AappYOUR_GOOGLE_LOAD_BALANCER_IPDefault

4. Resolve any conflicting app A/AAAA/CNAME record deliberately. Preserve unrelated MX, TXT, verification and email records.

5. Wait for DNS and the certificate to become ACTIVE. Check its status:

gcloud compute ssl-certificates describe zar-web-cert --global --project=$ZarProject --format="get(managed.status)"

6. Open https://app.zarintelligence.com. Check the certificate, sign-in, saved order, proofs and roster. Do not bypass a certificate warning.

7. After the domain works, restrict direct ingress:

gcloud run services update zar-polaris --region=asia-south1 --project=$ZarProject --ingress=internal-and-cloud-load-balancing

Use the custom domain thereafter. Confirm this restriction remains after later deployments.

Also using the root and www? If you intend to replace any existing website on those names, use this instead of the initial domain-creation command:

.\deploy\connect-domain.ps1 -Project $ZarProject -Domains @('app.zarintelligence.com','zarintelligence.com','www.zarintelligence.com')

Then point A records for app, @, and www to the same IP. If the load balancer already exists, add a certificate containing the additional names to the existing HTTPS proxy through Google Cloud Console, rather than rerunning resource creation.

References: Google's serverless load-balancer setup, GoDaddy subdomain records.

2. Sign in as owner → Administration → Users and roles.

3. Enter UID, name, email, role and Store6; save. Reusing a UID updates its access. Clearing Active disables access on its next request. Use the correct UID; email text alone does not identify the account.

10. What is live code, and what remains separate work

The implemented path is web brief → real-logo proofs → roster → deterministic quote → approval → confirmed production specification. Existing local examples remain labelled synthetic. Prices and print rules stay in the handbook's merchant policy files; approve them before accepting customers. Delivery confidence uses the existing assumptions, not a carrier guarantee.
